# Define the Work atom and context contract

Type: grilling
Status: resolved
Assignee: codex
Blocked by: 01, 03

## Question

What are the mandatory inputs, context budget, tools, outputs, evidence, retry rules, provenance, and completion semantics of a Work atom, and how does the Factory prove that each prompt contains sufficient but minimal authoritative context?

## Comments

## Answer

### Resolution — 2026-09-07

A Work atom is the smallest **cohesive, independently verifiable durable transaction**, not necessarily one prompt. A Model turn is the smaller inference operation inside an Attempt. An Attempt may use several bounded Model turns for localization, implementation, diagnostics, and explicit context expansion, but an accumulated conversation is never durable state.

The Work-atom and context contract is:

1. **Granularity.** One Work atom has one primary objective, bounded writable scope, declared outputs, deterministic completion checks, no unresolved product/architecture decision, and a context envelope that fits a validated tier. If these conditions fail, the Orchestrator decomposes the objective or explicitly promotes its context tier. Prefer the smallest cohesive and independently verifiable atom, not fragmentation for its own sake.
2. **Mandatory durable inputs.** The contract records stable atom and Graph-revision identities; objective and non-goals; requirement and Product-module identities; source/tree revision and precondition digests; writable and prohibited paths; dependency-artifact and upstream-contract references; Capability, network, credential, and sandbox profiles; allowed tool classes; required Evidence gates; context and Recovery budgets; expected typed outputs; and idempotency/integration keys.
3. **References, not prompt expansion.** Rich durable metadata is stored as identities, digests, and references. It is not copied wholesale into a prompt. The Context composer resolves only material required for the current Worker view; omitted material remains addressable through typed expansion.
4. **Purpose-specific Worker views.** Each worker receives the smallest projection required for its responsibility. A developer receives its objective, writable Product module, relevant contracts/source, diagnostics, and tests. QA/review receives authoritative requirements, candidate changes, affected contracts, and test facilities while remaining independent of developer reasoning. Localization receives structural/search evidence and read-only tools. Gate work receives policy and machine evidence rather than broad narrative. Workers share authoritative identities and artifacts, not transcripts.
5. **Independent evaluation.** Developer reasoning is non-authoritative and excluded from QA/review by default to reduce shared hallucination and self-approval. It may be retrieved as explicitly labelled evidence only when diagnosing a failure; it never substitutes for source, requirements, or checks.
6. **Context-manifest contents.** Each Model turn receives an immutable, content-digested Context manifest containing system policy and worker instructions; exact objective, non-goals, and output schema; acceptance criteria and current diagnostics; target Product-module contract; selected dependency/reverse-dependency contracts; exact authoritative source spans with revision, digest, and retrieval reason; applicable tests/policies/profile rules; relevant prior-failure evidence; section-level token accounting; an inventory of consequential omitted candidates; and permitted expansion operations. Generated summaries are visibly non-authoritative navigation aids.
7. **Adaptive context tiers.** Initial total input-plus-reasoning-plus-output tiers are 4K for experimentally validated trivial work, 8K routine, 16K expanded, and 32K exceptional. Above 32K is experimental until promoted by local evidence. The Context composer reserves output before selecting input. A versioned Context policy may automatically promote or demote preferred tiers per worker/atom class and Capability profile using measured success, latency, token use, coverage, and expansion behavior.
8. **Typed expansion.** A worker may request a named file, symbol, diagnostic, graph edge, or one-hop neighborhood. Each expansion creates a new Context-manifest revision with its reason and provenance. If sufficient material cannot fit, the worker requests decomposition or tier promotion rather than silently truncating authoritative evidence.
9. **Measured sufficiency.** GFLO does not claim to prove that an arbitrary prompt contains exactly sufficient context. It certifies provenance and required structural coverage, then evaluates Context policies through retrieval recall/precision, expansion frequency and rescue rate, stale-context detection, success versus tokens, ablation failures, and missing-dependency incidents.
10. **Broad autonomous tools.** Capability and sandbox profiles provide composable primitives rather than enumerating exact tasks. Inside its granted sandbox a worker may search the Internet, inspect unfamiliar formats, write helpers, download/install tools, run package managers/compilers, and combine tools in unplanned ways. External enforcement controls writable paths, network reach, credentials, resources, and host access. A worker may request but cannot self-grant authority outside Preauthorization.
11. **Capability learning.** A novel technique may be used ephemerally inside the current Attempt. The worker may propose a separate Work atom to make it persistent through a Capability-profile change with provenance, reproducibility, sandbox-policy, and regression evidence. Once accepted, later runs may use it automatically.
12. **Typed WorkerResult.** `WorkerRuntime` returns `candidate`, `needs_context`, `needs_decomposition`, `blocked`, or `runtime_failure`, plus output-artifact manifests/proposed changes, commands/tools used, checks run, evidence references, assumptions/risks, changed paths, dependency impact, suggested follow-up work, and final context/token accounting. A worker cannot return `accepted`.
13. **Evidence-derived retry context.** A retry receives the immutable contract plus a compact failure delta: failed checks, relevant logs, changed diagnostics, strategy classification, and prohibited repetition. It does not inherit the full transcript or treat prior reasoning as truth.
14. **Failure-directed treatment.** Missing known evidence expands the Worker view; wrong localization invokes specialized localization; excessive objective scope triggers decomposition; missing tools trigger capability discovery; adequate-context reasoning failure changes strategy; and a deterministic contradiction triggers quarantine/re-planning. Larger context is one treatment, not the universal retry.
15. **Content-addressed invalidation.** A Context manifest becomes stale when any keyed source/path digest, Product-graph revision, Work-atom contract, profile/toolchain, extractor/retrieval policy, prompt template, model/runtime profile, or prior evidence changes. Only affected derived views are rebuilt. A stale queued Attempt is cancelled, rebuilt, or superseded before mutation.
16. **Controlled decomposition.** A worker may propose a typed decomposition but cannot write the Work ledger. The Orchestrator checks scope, graph cycles, acceptance coverage, and capability availability before appending a Graph revision.
17. **Completion.** A Work atom is complete only when declared outputs exist and satisfy schemas, source/precondition digests remain valid, changed paths remain in scope, required deterministic gates and Product-graph constraints pass, evidence is durable, and the Work ledger atomically accepts exactly one result. Worker termination, a plausible patch, or model confidence is never completion.
18. **Empirical calibration.** Small-model sufficiency and ideal atom size remain hypotheses. Early real-Qwen stages must tune Worker views, token tiers, atom cohesion, specialization, and retry treatments using completion rate, integration failures, repeated-context cost, and wall-clock time. The contract permits those policies to evolve without changing its durable authority and provenance rules.
