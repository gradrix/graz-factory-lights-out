# Select the implementation foundation

Type: grilling
Status: resolved
Assignee: codex
Blocked by: 01, 02

## Question

Which implementation language, persistence layer, execution environment, and local-model worker harness should support GFLO's independent orchestration contracts, and what is the smallest foundation needed for the first real-model experiment?

## Comments

### Constraint refined by “Choose the durable orchestration architecture”

GFLO must own its orchestration implementation and formats. SFLO and Gas City are design references only: do not import, invoke, embed, preserve compatibility with, or build fallback paths to either. Select dependencies only for focused infrastructure leverage behind GFLO-owned seams.

### Proposed implementation foundation — 2026-09-08

Pending user discussion under Wayfinder; the recommendations below are not yet a resolved stack decision. They instantiate the accepted logical architecture without implementing all its layers up front.

Supporting evidence: [Implementation foundation: primary-source checks](../research/implementation-foundation.md). Documentation supports the infrastructure choices; no local hardware or worker-capability measurement was performed for this proposal.

1. **Language and packaging.** Use typed Python for the first independent GFLO implementation, packaged as a modular monolith with a CLI and one supervised reconciliation process. Prefer explicit functions and validated records over a framework-managed agent object graph. Start with standard-library SQLite, Pydantic for external record validation, and HTTPX for model transport; use pytest, Ruff, and a static type checker for development. Pin the tested Python and dependency versions in a reproducible lock/environment when building the experiment. Python is an iteration-speed recommendation, not a claim that it makes the local model smarter. Revisit language only for a measured bottleneck or maintenance problem, not speculative scale.
2. **Durable state and artifacts.** Use SQLite on local storage for the Work ledger, with explicit transactions, foreign keys, WAL mode, an explicit durability setting, and one logical writer. Keep inference, tests, and container operations outside database transactions. Store large immutable artifacts in a content-addressed local directory; durably publish artifacts before accepting their references in the ledger. Recovery reconciles incomplete operations and orphaned artifacts. Treat SQLite and artifact backup/restore as one consistency problem; do not copy only a live database's main file. Git records product revisions, not factory lifecycle authority. No Redis, external queue, PostgreSQL, or graph database is needed for the first single-host experiment; revisit only with measured contention or a real multi-host requirement.
3. **Execution arrangement.** Separate the trusted control plane and execution broker from disposable unprivileged worker/test containers and from the GPU model server. Prefer a dedicated rootless Docker setup for attempt execution when its resource controls are verified on the actual host. Only the broker gets container-management authority; workers get no daemon socket, canonical writable repository, ledger, or control-plane secrets. Containers are a practical initial isolation layer, not a guarantee against hostile kernel exploits; an inability to enforce required controls is a failed environment preflight, not permission to silently weaken isolation. Images and installed dependency sets are versioned. Broad outbound network and script execution remain available inside the existing preauthorization policy. Do not make every logical model role a permanently running container or GPU process.
4. **Model client and worker loop.** Implement one explicit GFLO-owned loop and one thin InferenceGateway using the first locally validated backend. The previous feasibility report nominates SGLang as the first candidate, not a hardware-verified installation. Probe the exact checkpoint revision, tokenizer/chat template, constrained-output/tool behavior, output accounting, and memory envelope before treating them as supported. Start with one inference request in flight. Validate structured results and tool requests outside the model, keep durable state out of chat history, and rebuild bounded Worker views between turns. Expose only the relevant tools and arguments; tool availability is not a reason to inject an entire tool catalog. Do not install an agent orchestration framework, SFLO, or Gas City as a runtime dependency or fallback. Add a second real backend only when needed; a configurable URL does not establish backend compatibility.
5. **Product support and graph representation.** Make a small Python library with a provider and two consumers, one nested, the first Capability profile. Use pytest-based executable acceptance and explicit contract/dependency manifests, checked against language/build evidence. Keep graph revisions and edges in ordinary records; derive bounded views with code rather than embedding a graph database or vector store. This limits the first experiment, not the factory's product architecture or eventual supported languages. A Python core does not imply Python-only products. Add a second product stack after a measured baseline so language-specific assumptions become visible.
6. **Worker context and autonomy.** Infrastructure dependencies stay in the factory implementation, not every worker prompt. A product worker sees its objective, relevant contract/code and direct dependency interfaces, allowed actions, and compact evidence. A worker changing a factory module receives that module's interface and the relevant dependency documentation, not a claim that infrastructure can always be hidden. Prefer coherent modules with small interfaces over hundreds of arbitrarily tiny files. Ordinary automatic retries, re-planning, and environment recovery remain factory responsibilities; this stack introduces no routine human checkpoints.
7. **Smallest executable slice.** First build only enough durable plumbing to submit a prepared Work atom, compose a bounded view, invoke the real model, run a candidate in isolation, collect trusted test evidence, accept or retry, and resume after interruption. Measure a developer/repair worker and a separate requirement-derived QA worker before implementing general manager hierarchies. Then exercise the provider/consumer change using a prepared graph; clearly label this as execution validation, not autonomous product-planning proof. Dynamic planning and graph discovery earn their next stage through measured results. Do not begin with a dashboard, distributed services, plugin platform, generalized workflow DSL, or self-modifying active runtime.
8. **Self-growth sequencing.** Keep the accepted Generation N/N+1 model: future factory changes are candidates produced in isolated workspaces, tested with copied state, and promoted by a separate preauthorized launcher. The initial slice does not need automatic self-upgrade to test local worker feasibility. Lack of that layer is recorded as incomplete factory capability, not advertised as the final lights-out product.

Decision trade-off: prioritize fast empirical iteration, explicit state transitions, and low operational complexity over a compiled standalone deployment or an existing agent framework's breadth. Reliability comes from the validated lifecycle and evidence protocol, not the language, schema validator, or container runtime alone. Numerical promotion thresholds and the final stage sequence remain in their existing decision tickets.

## Answer

The user accepted the proposed foundation after explicitly clarifying that the factory must be able to produce technologies other than Python. Adopt the eight-point proposal above with that clarification as a binding design constraint, not a claim of already implemented capability.

Python is the factory implementation language and the first controlled product experiment only. Product-language support belongs to versioned Capability profiles: prepared toolchain/environment, contract and dependency extraction, build/test/acceptance commands, and focused technology-specific worker guidance. The core lifecycle and acceptance rules must not assume Python imports, packaging, test output, or runtime semantics. Stack-specific evidence is normalized into the existing factory records without losing its provenance or coverage limitations.

Later products may combine multiple profiles and languages through explicit, versioned cross-language contracts. A worker receives its own module context and relevant shared interfaces, not every language's documentation or the entire mixed-language product. Separate language competence does not establish cross-language integration competence; both require executable evidence.

Start with the proposed Python provider/two-consumer experiment, then validate a second product language after the baseline. The second language is intentionally not selected yet. Its experiment must demonstrate coding, repair, graph/interface extraction, and acceptance without rewriting the core lifecycle. Follow with a mixed-language contract migration and integrated product checks before claiming mixed-stack support. A toolchain installation alone cannot promote a Capability profile to supported status; autonomous capability discovery remains subject to the accepted validation rules.

This resolves the implementation-foundation choice. It does not certify the exact local model/server configuration, broaden publication authority, or authorize skipping the remaining evaluation and staged-plan decisions.
