# Set feasibility and evaluation thresholds

Type: grilling
Status: resolved
Assignee: codex
Blocked by: 01, 02, 03

## Question

Which greenfield and existing-repository workloads, baselines, quality measures, architectural measures, intervention rates, failure budgets, context costs, and unattended durations will distinguish a feasible local Factory from a compelling demo?

## Comments

### Proposed evaluation contract

Pending user discussion under Wayfinder. All numbers below are proposed initial engineering thresholds, not measured results, industry standards, or guarantees. They decide whether to expand a capability claim or architecture layer, not whether the user may continue research. Existing ten-attempt atoms, autonomous re-planning, configurable run budgets, and non-disableable authority/host-survival invariants remain unchanged.

1. **Evidence and experimental discipline.** Pin model/checkpoint, quantization, runtime, tokenizer/template, prompts, Context policy, tool profile, environment, validator versions, and workload revision for each campaign. Separate development fixtures from held-out evaluation tasks. Freeze criteria before scoring; never retune on hidden answers and report the same cases as unseen. Report task counts and raw outcomes, not only percentages. Repeated runs of a task measure variability but are not independent new tasks. Benchmark output is local evidence, not proof of general large-project ability.

2. **Smoke test before a full campaign.** Start with twelve small tasks covering bounded implementation, defect repair, consumer migration, and requirements-derived tests. Use the actual local model and isolated execution, not mocked inference. This diagnostic pilot checks whether the plumbing works and identifies unusable schemas or context views; it has no advertised pass-rate claim. Do not build manager layers to conceal a failing basic worker loop. Loading the model and a successful HTTP response are setup checks, not coding-feasibility results.

3. **Atomic work threshold.** After pilot fixes, evaluate forty held-out tasks: ten each for bounded implementation, defect repair, consumer migration, and requirements-derived test generation. Run three fresh repetitions per task, for 120 task runs. Initial progression target: at least 108/120 independently verified completions within the original atom's ten-attempt policy, at least 24/30 in every task class, and no discovered false acceptance. Record first-attempt success, attempts to success, model turns, and terminal or inconclusive outcomes separately. Any unfinished or inconclusive run stays in the denominator. Re-planning into replacement atoms is measured separately as eventual objective completion; it cannot reset this within-ten score or hide costs. Task-generated tests count as successful only when they accept the known-good implementation and detect their task's independently seeded required defect cases, rather than merely execute successfully.

4. **Acceptance integrity and recovery.** Before expanding the tested scope, require zero invariant violations in a versioned fault suite. Initially exercise at least five variations of each: missing/skipped required tests, forged success evidence, stale inputs, duplicate delivery/expired leases, worker death, model-server death, gate-runner death, controller restart during artifact publication/acceptance, controlled disk-reserve exhaustion, and attempted writes outside granted authority. Use isolated fault fixtures, not destructive host exhaustion. Assert no false acceptance, no lost accepted history, no duplicate acceptance, and no unauthorized writes. After removal of transient faults, interrupted work must resume automatically or produce an evidence-backed terminal exception where the existing contract requires one; quarantine alone does not prove successful recovery. Bound recovery observations using predeclared lease/restart deadlines and flag missed deadlines. Every fault category must pass; aggregate success cannot hide a broken invariant. Zero observed defects is only a finite-suite result.

5. **Small-context target.** Compare 4K, 8K, 16K, and exceptional 32K total-context tiers, only where the exact server profile supports them, including output/reasoning capacity rather than counting user text alone. Initially target at least 80% of successful task runs having no Model turn above 8K. Report the same fraction across all runs, mandatory-context omissions, expansion frequency/rescue, retrieval coverage on annotated fixtures, and cumulative tokens/time so this cannot hide difficult failed cases or many tiny calls. This is a diagnostic target, not a correctness gate: if 16K reliably solves tasks that 8K cannot, revise the role-specific policy and accurately narrow the small-context claim. Never truncate necessary interfaces to meet a headline budget. Log unsupported tiers instead of assuming the advertised model window fits the GPU.

6. **Independent QA and additional layers.** First evaluate the QA worker separately on twenty distinct seeded-defect candidates and twenty known-good candidates, with defects checked by independent executable evidence. Initial target: reproduce at least 18/20 defects and make no more than 2/20 unsupported defect reports on known-good candidates. Then compare the simple worker loop with added QA on the same held-out tasks and inference configuration, counting all extra model calls and recovery work. Hierarchy gets its own later comparison against a flat scheduler on cross-scope tasks. Retain added layers only with reproducible improvement in verified completion or defect detection without worsening acceptance integrity; small or inconsistent differences remain inconclusive. Shared-model reviewer agreement is not independent proof. Missing the QA target blocks reliance on that QA capability, not unrelated deterministic verification work.

7. **Integrated changes and maintenance.** After atom-level results justify proceeding, run ten distinct provider/two-consumer change scenarios, including a nested consumer, breaking contracts, behavior-preserving refactors, stale consumers, and intentionally incomplete graph evidence. Repeat each three times. Initial target: at least 27/30 fully verified integrated completions with no discovered false completion; consumer coverage and contract pins must be evidenced. At this stage use prepared work graphs and label the result execution competence, not autonomous planning competence. Follow with twenty held-out maintenance tasks across at least two existing fixture repositories, targeting at least 18/20 verified completions without manual rescue and no discovered false acceptance. Preserve base failures as explicit debt. Maintenance repositories must be unseen during campaign tuning; do not claim they were absent from model training. A run's observation window is fixed in its campaign manifest before scoring; incomplete cases remain incomplete even if the factory is allowed to continue afterward.

8. **Autonomy, duration, and scale.** Progress from an eight-hour active shakeout to a 72-hour unattended campaign. The latter must include at least 100 accepted atoms and twenty integrated changes, planned fault injections, complete attempt/replan accounting, and zero manual repair, prompt edits, or decision interventions during the scored run. Fault injection and passive observation are not manual rescue. Require at least 90% of scheduled feasible objectives to reach verified completion within the declared observation window; report terminal exceptions and unresolved work separately. Idle uptime or repeated trivial tasks cannot substitute for the declared workload mix. Restart after a corrective implementation change begins a new qualifying soak, preserving the failed record. These durations are benchmark windows, not mandatory production run limits. Later scale tests increase repository size, graph depth, and coupling independently, including modular monoliths; evaluate autonomous plan creation and graph discovery separately before claiming end-to-end large-product ability. Support claims describe the largest tested size/coupling envelope, not unlimited codebases.

9. **Multiple technologies and future models.** After the Python baseline, require a second language to pass an equivalent per-profile atom/integrity campaign without rewriting core lifecycle semantics. Before claiming mixed-language support, run ten distinct cross-language contract migrations targeting at least nine fully verified completions and zero discovered false completion. The choice of second language belongs to the staged plan. Replacement models repeat relevant calibration and held-out regression campaigns; a model name or vendor benchmark cannot inherit a prior profile's support status.

10. **Costs, failed thresholds, and honest claims.** Report wall time, token use (including retries/re-planning), GPU memory, peak host resource use, and energy only where measurable with a stated measurement scope. There is no minimum tokens/second or maximum electricity-cost target for this user's feasibility decision. Version campaign deadlines and optional budget settings so a hung case remains visible and runs remain comparable; they do not impose a new non-disableable global run cap. Numerical research thresholds may be revised prospectively with a recorded rationale and a fresh campaign; a relaxed criterion cannot retroactively turn an old result into a pass. Acceptance integrity and mandatory product requirements cannot be waived by benchmark configuration. Below-target results mean diagnose, narrow the capability claim, or revise the next experiment—not silently add managers, weaken tests, or declare the whole ambition impossible. Autonomous experimentation may continue inside preauthorization without a routine human checkpoint.

### Code-quality clarification requested during discussion

Include automatic code-quality evaluation explicitly in each Capability profile, for both generated products and candidate factory changes. Trusted tooling collects build/type errors, lint/format violations, test and branch coverage, complexity, duplication, dependency/architecture violations, and applicable security findings. Configure supported checks and their severity before the run; a missing required analyzer is inconclusive, not a passing quality result. Workers receive focused findings and relevant code, not whole-repository reports.

CRAP (Change Risk Anti-Patterns) combines cyclomatic complexity and test coverage; see the [original metric discussion](https://www.artima.com/weblogs/viewpost.jsp?thread=215899) and [PHPUnit coverage documentation](https://docs.phpunit.de/en/13.4/code-coverage.html). Include it where the profile can reliably associate complexity and coverage with the same code unit and revision. Record analyzer versions and coverage semantics; do not compare unlike language/tool scores as if identical. Missing coverage means unavailable evidence, not an invented good score.

Proposed treatment: deterministic mandatory build/type/contract checks block acceptance on failure; calibrated quality rules can also be mandatory in a profile. CRAP, complexity, duplication, and coverage initially identify hotspots and trigger focused test/refactor work rather than impose an uncalibrated universal numeric cutoff. Track changed-code regressions and existing debt separately, while still enforcing mandatory criteria for the current task. Candidate workers cannot waive rules, insert suppressions, or exclude code merely to pass; legitimate exceptions or policy changes require the existing traceable validation path. Low CRAP or high coverage cannot establish correct behavior, good module interfaces, or adequate assertions. Use seeded defects/mutation and integration checks to resist metric gaming; splitting code into trivial wrappers is not evidence of improved modularity.

### Cross-language evaluation requirements

After the Python baseline, measure a second product language's coding, repair, contract/dependency extraction, and acceptance through a Capability profile without rewriting the core lifecycle. Then test a mixed-language contract migration with integrated acceptance checks. Report per-profile and cross-profile results separately; installed toolchains or success in one language do not demonstrate another language's support. The exact second language and numerical promotion thresholds remain to be selected.

### Constraint surfaced by “Design verification and recovery gates” — 2026-09-08

Measure narrow requirement-derived test generation, defect reproduction, bounded repair, and consumer migration separately on the real local model. Compare a simple worker loop against added independent QA and hierarchical planning on the same workloads; retain complexity only when measured results justify it. Include deliberately wrong candidates, missing/skipped tests, forged success text, stale inputs, and interruption. Report false acceptance and inconclusive outcomes alongside verified completion. Separate missing-context failures from semantic capability failures; more retries, context, or managers are not assumed to cure either. Deterministic runner and acceptance bookkeeping must not consume each worker's prompt budget.

### Large-project and model-evolution requirements — 2026-09-08

Evaluate both repository size and change coupling, including modular monoliths, internal libraries, and existing projects. Begin with one provider/two consumers and expand to cross-scope migrations, repeated extensions, and unfamiliar maintenance tasks. Report verified completion, undetected regressions, recovery, elapsed time, energy where measurable, and cumulative rework. Time/energy availability permits longer experiments; it does not substitute for correctness evidence. Compare future local models against identical workloads and recalibrate context/tool policies before promotion.

### Constraint surfaced by “Choose the durable orchestration architecture”

Evaluation must begin with a thin durable walking skeleton and a small set of logical workers using the real local Qwen3.8-27B/RTX 5090 service. Define falsification thresholds for typed results, small-context sufficiency, retries, crash recovery, and tiny end-to-end tasks before permitting higher architecture layers.

Measure 4K/8K/16K/32K Context policies per worker/atom class, role-specific Worker views, retrieval recall/precision, expansion rescue rate, stale-context detection, success per token and wall-clock hour, atom cohesion, integration failures, and the value of specialized versus general workers.

## Answer

The user accepted the recommendation and requested progression to the next stage. Adopt the ten-point evaluation contract and the explicit code-quality clarification above. The numerical targets are initial, prospectively revisable campaign criteria, not observed results or new mandatory production run budgets. Preserve both successful and failed campaign evidence; never relax mandatory product acceptance or authority invariants to improve a benchmark score.

Automatic quality checks are profile-owned and run by trusted tooling outside worker prompts. Mandatory build/type/contract rules block acceptance; CRAP and similar metrics initially identify test/refactor hotspots unless a calibrated profile explicitly makes a rule mandatory. Support claims require the scoped local-model, recovery, integration, maintenance, and language evidence specified above. Further experimentation remains permitted when a target is missed.

The next architecture prototype must visibly distinguish simulation from measured behavior, correctness gates from advisory quality findings, original-atom attempts from replacement-atom recovery, and prepared execution graphs from future autonomous planning.
