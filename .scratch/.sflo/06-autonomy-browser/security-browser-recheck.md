## B5 — guardian facts permission depends on umask, reader requires0644

**New v3 defect, high confidence; interrupted-work recovery becomes unavailable under ordinary process umasks.** `browser_pair.main` creates `facts.json` using `open(path,'x')` without an explicit final mode. `BrowserStore.cleanup` then validates that file using `checked_file(...,0o644)`, whose mode comparison is exact. With umask002 the writer creates0664; with umask077 it creates0600. Both cause `Document record file type/owner/mode/size changed` before acknowledgement can proceed. Umask022 produces0644 and recovery succeeds.

[modes.py](security-browser-recheck/modes.py), [mode-results.json](security-browser-recheck/mode-results.json) reproduce all three paired cases through the same file-creation primitive and actual cleanup reader. The initial full recovery probe failed at this check under the current umask002; it was subsequently split into explicit failing mode probes and an intended-mode recovery control. Source inspection establishes the production writer uses that primitive. These permission probes do not claim actual container owner death was repeated for v3.

The failure is closed: the fence remains and no new result is falsely accepted. It nevertheless prevents promised explicit recovery after retained guardian facts, including owner interruption. Smallest repair: set the guardian facts mode explicitly to its required value, retaining controller ownership, regular-file and link checks. Recheck writer output under002/022/077 and actual owner-death recovery against the next immutable candidate. Coordinator and builder were notified immediately; they authorized this focused follow-up.
