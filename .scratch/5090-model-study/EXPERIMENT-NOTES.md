# Experiment notes

- Scope: single RTX 5090 in MONSTER-GAMING-PC, WSL2, September 30 2026. Default use case is local coding and agent work; no answer was received to the optional workload-preference question.
- Original service is preserved as `local-vllm`. Temporary servers use `benchmark-5090-server`, bind only host loopback port 18000, and use downloaded files under `/home/gradrix/benchmark-5090`.
- Original container inspect (including environment secrets) is saved only on the rig in a mode-0600 file; local inventory is sanitized. Restore: `python3 /home/gradrix/benchmark-5090/profiles.py restore`.
- Three speed runs use 256 output tokens; first run includes cold/wakeup effects. Compare warmed `speed_1` and `speed_2`. This is single-request decoding, not aggregate throughput.
- All initial quality tasks disable thinking, temperature zero, 768 output-token ceiling. Agent turns use 1024. This measures a bounded zero-temperature operating mode, not maximum reasoning quality or a public leaderboard.
- Eight Python tasks are executed in disposable Docker containers with no network, no mounts, read-only root, dropped capabilities, 128 MB memory, 1 CPU and a 20-second deadline. Three tool-argument tasks and one JSON task complete the twelve-case smoke suite.
- Agent tests expose a synthetic one-file project and three narrow tools: read, write and tests. They are small repair workflows, not full SWE-bench or a GFLO production pilot.
- Baseline `repair_events` overlapped the two baseline randomized context probes. Use their correctness results, but exclude their wall time from serial latency comparisons. Baseline throughput and twelve-case suite were serial and unaffected.
- Original simple context probes reuse repetitive filler and may benefit from prefix caching. They establish successful requests, not cold prompt-processing throughput. Later `context_stress.py` uses unique random distractors, three facts at 10/50/90 percent depths, an absent-key check, two seeds, and actual server token counts.
- Context probes reserve output space. “32K configured” is not the same as “32K input”: prompt, formatting and output share the window.
- Tool parser buffering makes `decode_tokens_s` unreliable on tool-call turns. Use fixed text speed runs for generation-speed comparisons.
- API-key values and the original private container inspect must not be copied into the repository.
- Older 96K vLLM artifact filenames contain `f16`; their recorded launch command actually uses `--kv-cache-dtype fp8`. Historical filenames are retained, and the report uses the executed configuration.
- The 32-task HumanEval subset was chosen by `random.Random(5090)` before seeing model outputs. All 164 tasks were eligible (stdlib only). Every selected canonical solution passed in the exact Python 3.11 sandbox before model evaluation. Chat requests ask for a complete module; the grader appends the unmodified published tests and `check(entry_point)`. This differs from the original completion-based harness and is explicitly not an official full pass@1 result.
- vLLM 128K with single-size decode CUDA graphs failed capacity validation: required KV 4.31 GiB, available 2.49 GiB, estimated supported length 72,128. Eager 96K succeeded and answered both 96.5K prompt probes. Preserve both outcomes rather than treating compile success as serving success.
- Hardware detail: the host is a Ryzen 7 9800X3D, but WSL currently exposes only four logical CPUs. Host-offload results apply to this WSL configuration. CPU allocation was not changed.
- Total GPU memory at Bonsai 32K readiness was 10,740 MiB (10.49 GiB), including the desktop/driver allocation. The conversational approximation of 10.7 GiB should be read as this measured value.

- Flash 131K Q8 allocation succeeded at 32,065 MiB total GPU, but only a 31,504-token input was completed in that profile. It took 232.45 seconds and retrieved all four values inside a Markdown JSON fence, which fails the strict JSON contract. The queued near-131K probe was deliberately cancelled to compare a 64K allocation with a larger microbatch; this is not an OOM or a demonstrated 131K correctness failure.
- The subsequent Flash 64K/Q8/microbatch 512 profile repeated the identical 31.5K input in 37.11 s (all values present, JSON fence again). Both allocation and batching changed, and host PLE file pages were warmer, so the improvement cannot be attributed to batching alone. This was not a cold SSD-cache comparison.
- A fresh near-131K Flash Q8/microbatch 512 probe was also cancelled during prefill after very low progress (the preserved log records token/time points). This is a latency boundary, not a completed correctness result. The subsequent Q4 profile completed its near-131K probe; see RESULTS.md.
- The later graph-enabled vLLM restart reported 4.59 GiB KV (129,706 pooled tokens) rather than the earlier 2.36 GiB. Estimated graph memory was 0.42 GiB, actual capture 0.04 GiB; startup consumed memory 24.01 GiB and peak activation 0.70 GiB. This invalidates treating the initial 128K failure as a permanent hardware limit; the subsequent explicit 4.5 GiB KV profile validated the 131072 window on two near-limit requests. Startup profiling/cache state is a possible contributor, not a proven cause.
- Graph vLLM's earlier four-task thinking spot check failed HumanEval/116, while the later full-run response to that task passed. Temperature zero does not establish repeatability across these runtime runs; retain both outcomes rather than treating a single perfect subset result as proof of universal reliability.
