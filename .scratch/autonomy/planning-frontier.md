## Smallest useful slice

One accepted product increment, one clean source commit, one frozen prepared environment, **two or three dependent tasks executed serially**, and one private integration repository. One local model proposes a plan in a fresh context; a separate fresh-context review checks it against the already accepted requirements and acceptance proposal. Persist the approved plan before dispatch. The controller selects ready tasks, owns shared limits and integrates verified candidates. Return a reviewable aggregate patch and complete integration receipt; do not write the original repository or add deployment.

Start with2–3tasks rather than the roadmap's eventual2–5. This is a useful subset, not fullStage5 completion. No concurrent workers, arbitrary team hierarchy, dynamic tool discovery or general workflow framework. If decomposition does not improve the frozen comparison, retain the planner as advice and keep direct execution as the default.

## Data and state boundaries

1. **Accepted increment:** frozen brief and explicit requirement IDs; source commit/tree; supported environment receipt; independent full-increment acceptance bundle/hash; allowed operations and aggregate budget. Acceptance criteria are proposed/reviewed before implementation. In the first qualification, independent fixture authors supply executable checks. Model-authored acceptance remains a proposal, never automatically trusted code.
2. **Plan revision:** immutable parent contract hash, revision/previous-plan hash,2–3stable task IDs, objective/requirement ownership, dependencies, expected interface changes and declared scope. Planner receives bounded source and public criteria, not hidden oracle/reference implementations. Deterministic validation rejects cycles, missing IDs, unmapped requirements, unsupported environments and invented check commands. A separate review can reject missing integration responsibilities or invented policy; schema validity alone is not semantic approval. Persist reviewer decision and controller approval identity/policy before dispatch.
3. **Dispatch:** controller-owned binding of plan hash, task ID, exact integration tip, dependency acceptance IDs, environment and reserved remaining budget to one existing child run. Workers see their objective, required interface facts and relevant failure evidence. They cannot edit the plan, parent database, approval/check bundles or Git integration metadata.
4. **Integration:** verify child acceptance is still intact; apply its bound patch in fresh private staging at its **exact dispatch base**; compare resulting candidate with the accepted child fingerprint; run preserved-behavior checks plus the independently frozen cumulative checks due at this step and review. Publish the new private integration tip/receipt only if those checks pass and expected tip is unchanged. After all tasks, run the complete original increment oracle/journey; interim acceptance never substitutes for that final gate or fails a task merely because later planned features are not implemented yet. Keep the previous good tip on conflict, cancellation or failed checks. Do not auto-rebase stale patches or silently resolve conflicts. Original source remains untouched; exported aggregate patch names its original expected base.
5. **Repair/revision:** failed integration yields stable check IDs, candidate/base identities and bounded diagnostics. Requirement ownership identifies the responsible task; ambiguous cross-task ownership stops for plan revision rather than an invented attribution. Create a new child run on the retained integration base, attach failure evidence, and debit the same parent budget. A revised plan is a new immutable revision; preserve previous attempts. Reuse completed work only when exact input/dependency hashes still match; descendants of changed inputs become stale. Two repeats of the same failure on the same candidate stop; repairs cannot reset the budget.

Minimal parent states: `proposed → approved → running → checking → accepted`, with explicit `needs_input`, `exhausted`, `cancelled`, `interrupted`, and `invalidated`. Child runs keep existing states. An append-only dispatch/integration record makes restart distinguish “child accepted, integration not published” from completed integration; resume revalidates receipts and avoids duplicate dispatch. Cancellation stops scheduling, cancels the active child, waits for owned cleanup, and cannot publish parent success. One controller lease covers the parent increment; do not call the existing nonreentrant Factory lock recursively.

For the first serial scheduler, every dispatched task starts from the current verified tip, including ready siblings; there is no claim of parallel branch merging. Injected overlap/conflict is a **refusal and explicit repair/revision** control. Broad autonomous conflict resolution is a later capability.

## Six-case direct versus decomposed qualification

These are proposed case shapes, **not authored/frozen fixtures or unseen qualification evidence**. An independent author should build six fresh4–8module projects with realistic existing behavior, precise policies/types/errors, tests and usage documentation; prove missing-feature starter failure and conforming-reference success in exact prepared environments before model exposure.

| Case | Coherent increment | Why a split may help / integration trap |
| --- | --- | --- |
| CLI expense ledger (stdlib) | Atomic CSV import with explicit duplicate policy, plus category totals and CLI export | Import validation/domain persistence/report agree; malformed late row must not partially commit. |
| CLI backup catalog (stdlib) | Content metadata scan and deterministic restore-plan command under explicit retention rules | Shared path/identity rules and stable output; independently passing modules can disagree about relative roots. |
| Packaged appointment API | Idempotent create/update requests and queryable appointment state | Domain key semantics, HTTP status/schema and persistence must agree; no invented scheduling policy. |
| Packaged measurement API | Bounded batch ingestion and window summaries with explicit ordering/missing-value rules | Validation, storage and summary units/half-open boundaries can drift across tasks. |
| CommonJS TypeScript job queue | Durable job-state transitions with bounded retry policy and operator CLI | Serialization/schema compatibility and restart behavior; all policy values fixed in brief. |
| Owned Node ticket app | Create/edit/filter ticket journey with stale-version feedback | API/UI contract and preserved routes; final fixed Playwright journey observes real behavior and reload persistence. |

Use the same initial commit, public requirements, environment, final oracle, model/profile and **aggregate ceiling** for both arms. Suggested freeze starting point:48total model requests,32,768total generated tokens including reasoning,1800seconds operation work plus separately bounded cleanup; controller reserves remaining tokens/time before every request, including planning, plan review, code review and question assessment. Both arms get at most one approved plan revision/integration repair allocation from that same pool, not extra attempts per task. Numeric limits are a proposed experiment contract, not current runtime support; validate feasibility before freezing, then do not increase after failures. Equal ceilings do not imply equal consumed budgets.

Direct receives the full increment as one task and the same final checks/review. Decomposed pays its planning/review overhead from the same pool. Fresh conversations and isolated workspaces; alternate arm order across cases; preserve cache/order and token/latency observations. Same-model correlation remains a limitation. No reference code or hidden expected answers enters planner/worker/reviewer context.

Freeze deterministic controller fault controls alongside the cohort: changed source/expected tip, overlapping stale patch, missing/cyclic dependency, cancellation between child acceptance and integration, and unit-pass/integration-fail. Apply equivalent base/cancellation/integration controls to direct execution where applicable. These controls establish safety/recovery; do not count deliberate aborted controls as six successful product increments. Ensure feedback reaches the mapped responsible task and identical failure stops within the shared budget.

Score each complete increment only after every requested fact/behavior, preservation requirement, generated tests/docs, final integration check and independent semantic review passes. Record false acceptance/missed requirements, substantive human interventions and their time, clarification stops, all repairs, calls/tokens and end-to-end time. Promotion requires more fully accepted increments, or equal accepted outcomes with fewer substantive human interventions, **without increased missed requirements**. Count plan-approval effort too; do not hide human work in fixture adjustments. Six paired cases provide a directional gate, not statistical proof or broad-project reliability. Preserve a zero-benefit result and keep planning advisory.

## Route after unit07 acceptance

Freeze one bounded planning contract and independent six-case/fault corpus first. Implement parent plan/dispatch state plus shared budget and one serial integration path, with behavior-first controlled worker/reviewer tests; reuse existing child execution rather than replacing it. Independently review lifecycle, stale-base/acceptance authority and publication behavior. Then run the paired actual-model cohort with immutable inputs and no test edits after exposure. Broaden task count, project size, tool delegation or production integration only from that evidence. Unit07 acceptance alone does not authorize claiming Stage5 delivered.
